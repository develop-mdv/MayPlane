# ezdeploy

Русскоязычная веб-панель для управления проектами на нескольких Linux-серверах. Первая версия для одного владельца: Docker Compose, публичные Git-репозитории по HTTPS и SSH под root. Панель и исполнитель запускаются отдельно.

## Что работает

- Проекты, серверы, поиск и фильтрация, история операций и логи.
- Добавление SSH-сервера с проверкой SHA-256 ключа и входом по паролю или ключу без passphrase.
- Установка Docker, Compose v2 и Git на Ubuntu 24.04 по кнопке.
- Загрузка `.env`, шифрование секретов AES-256-GCM, SQLite для постоянных данных.
- Деплой, перезапуск и остановка Docker Compose. Несколько проектов на сервере имеют отдельные Compose project names.
- GitHub push webhook с HMAC-SHA256, проверкой репозитория/ветки и защитой от повторной доставки.
- Снимок CPU/RAM/диска при подключении или нажатии «Проверить», последние 200 строк контейнерных логов.
- Перенос образов, каталога проекта и управляемых Docker volumes с остановкой контейнеров, проверкой SHA-256 и возвратом к источнику при ошибке, когда это можно подтвердить безопасно.
- Деморежим без сервера. Примеры IP/репозиториев не являются реальной инфраструктурой. Изменения деморежима существуют только до обновления страницы.

## Локальный запуск

Требуется Node.js 24 и npm. Выполняйте команды в папке проекта:

```sh
npm ci
npm run runner:setup
npm run runner
```

В другом терминале:

```sh
npm run dev
```

Откройте `http://localhost:3000`. В «Настройки → Подключить исполнитель» укажите `http://localhost:8788` и значение `EZDEPLOY_TOKEN` из `.env.runner`. Настоящие записи загружаются после подключения; демонстрационные записи не отправляются исполнителю. Ключ панели хранится только в памяти вкладки. После перезагрузки подключитесь снова.

Файл `.env.runner` создаётся один раз и не перезаписывается. `EZDEPLOY_ENCRYPTION_KEY` расшифровывает секреты в `.runner-data/ezdeploy.sqlite`. Резервируйте **базу вместе с ключом**, храните их вне Git. Резервную копию SQLite делайте после остановки исполнителя либо штатным SQLite backup API; не копируйте только основной файл во время записи WAL.

## Доступ к исполнителю с опубликованной панели

Панель в Sites сама не устанавливает SSH-соединения. Разместите `runner` на своём сервере и выдайте ему HTTPS-адрес через обратный прокси. HTTP допустим только для локального запуска; HTTPS-панель и браузер могут запрещать подключение к локальной сети.

В `.env.runner`:

```dotenv
HOST=127.0.0.1
PORT=8788
ALLOWED_ORIGINS=https://your-panel.example.com,http://localhost:3000
EZDEPLOY_PUBLIC_URL=https://runner.example.com
```

Пример Caddy:

```caddyfile
runner.example.com {
    reverse_proxy 127.0.0.1:8788
}
```

Не открывайте незашифрованный порт исполнителя в интернет. Авторизация — один длинный ключ владельца, без регистрации/ролей/команд. CORS разрешает только перечисленные origins; вызовы без Origin (GitHub, CLI) всё равно проверяют ключ или подпись webhook.

Исполнитель можно запустить контейнером:

```sh
npm run runner:setup
docker compose -f compose.runner.yaml up -d --build
```

Порт контейнера привязан к loopback хоста. Данные сохраняются в отдельном named volume. Docker socket хоста исполнителю не нужен: он управляет целевыми серверами через SSH.

## Первый проект

1. «Серверы → Добавить сервер»: IP, порт, root-доступ. Сравните отпечаток с консолью своего VPS. Например, на сервере: `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256`. Тип ключа должен совпадать с согласованным SSH-ключом; fingerprint API показывает выбранный ключ сервера.
2. Если Docker отсутствует, нажмите «Настроить сервер». Установка рассчитана на Ubuntu 24.04. Уже подготовленные Linux-серверы с Bash, Git, Docker и Compose v2 тоже можно подключать.
3. «Новый проект»: публичный HTTPS URL, ветка, тип, сервер, Compose-файл и `.env` до 64 КБ. Поддерживаются однострочные `KEY=value`, комментарии и кавычки; многострочные значения отклоняются.
4. Откройте проект и нажмите «Развернуть». Рабочие каталоги: `/opt/ezdeploy/<uuid>/repo`. Не вносите туда ручные изменения: Git обновляется через `reset --hard`. Данные приложения храните в named volumes или bind mounts, которые не отслеживаются Git.
5. Compose использует имя `ez_<uuid>`. Не задавайте общие `container_name`, имена сетей и порты для разных проектов. Панель не выбирает свободные порты автоматически.

Пример приложения с проверкой состояния и сохраняемыми данными находится в `examples/node-app/`. Поместите его содержимое в свой репозиторий. Переменные для приложения задавайте в Compose через `environment` или `env_file: .env`; автоматическая подстановка Compose сама по себе не передаёт все переменные в контейнер.

`up --wait` проверяет Compose healthcheck, если он объявлен; без healthcheck проверяется только запуск контейнера. Добавляйте проверку готовности приложения и базы данных. Домен в форме — метка для панели; DNS, reverse proxy и TLS настраиваются отдельно.

## CI/CD

Укажите `EZDEPLOY_PUBLIC_URL`, откройте проект → CI/CD, включите автодеплой и создайте секрет. Добавьте URL и секрет в GitHub → Settings → Webhooks: `application/json`, `Push events`. Секрет показывается только при выпуске; перевыпуск требует обновления GitHub.

Исполнитель принимает только подписанный push в сохранённую ветку указанного репозитория. При занятом сервере webhook возвращает 409: используйте Redeliver в GitHub после завершения операции. Это простая очередь одного исполнителя; автоматические повторы и планировщик пока отсутствуют. Деплой забирает актуальный HEAD ветки, а не обязательно SHA конкретного события.

Workflow `.github/workflows/ci.yml` проверяет сам ezdeploy: тесты, типы и сборку. Автодеплой управляемых проектов выполняет webhook-исполнитель.

## Перенос и ограничения

Перед переносом сделайте отдельную резервную копию и убедитесь, что возможен простой. В первой версии поддерживаются одинаковые архитектуры CPU, локальные тома под управлением проекта и bind mounts внутри его каталога. Исполнитель отклоняет внешние/общие/анонимные тома, нестандартные драйверы, внешние сети и Compose secrets/configs. Внешние БД, S3, DNS и другие сервисы в перенос не входят.

Порядок: проверка → остановка → архив каталога и томов → экспорт Docker-образов → передача SFTP → сравнение SHA-256 каждого архива → восстановление → запуск без пересборки → Compose healthcheck. Для копий требуется свободное место на обоих серверах; запас рассчитайте заранее. Архивы и исходные данные сохраняются. Смена серверного ID происходит только после успешного запуска цели.

Если цель не запускается, исполнитель пытается остановить её и запустить исходный проект. Если остановку цели нельзя подтвердить, исходник автоматически не запускается: проверьте оба сервера вручную, чтобы избежать двух записывающих копий. При аварийном завершении самого исполнителя незавершённая операция помечается ошибкой и автоматически не повторяется. Остатки переноса не удаляются; следующий перенос на ту же цель будет заблокирован до ручной проверки и освобождения каталога/томов. Нет автоматического возврата после успешного переключения или синхронизации новых записей обратно.

Статус проекта — результат последней операции, а не непрерывный мониторинг. Метрики серверов и логи приложения запрашиваются вручную. API возвращает последние 100 операций (полная история остаётся в SQLite), до 2000 строк на операцию; нужен собственный долгосрочный сбор логов. Редактор маскирует точные значения `.env`; приложения не должны печатать секреты в другом кодировании.

Это MVP для доверенных репозиториев и одного владельца. Dockerfile/Compose выполняют код с широким доступом к целевому серверу. Приватные Git-репозитории, автоматический TLS, посторонние существующие проекты, роли, расписания бэкапов, непрерывный мониторинг, беспростойный деплой и перенос внешних БД ещё не реализованы.

## Проверки

```sh
npm test
npm run typecheck
npm run build
npm audit
```

Тесты поднимают локальные HTTP/SSH-серверы, проверяют авторизацию, подписи webhook, повторную доставку, шифрование, редактирование `.env`, сохранение данных и блокировку неподдерживаемого переноса. Деплой и перенос на настоящих VPS не проверялись: реальные серверы не предоставлены.
