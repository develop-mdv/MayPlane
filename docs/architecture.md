# Рабочее пространство ezdeploy

## Модель

**Сервис = развёрнутое приложение. Проект = рабочая папка агента. Чат = нативный диалог, с проектом или без него.**

Один проект привязан к одной машине. Одинаковый репозиторий можно добавить на несколько машин как отдельные проекты. У каждого диалога свой нативный ID Codex/OpenCode; смена раздела не запускает задачу повторно. Модель и режим доступа выбираются при создании диалога. Архивирование сохраняет историю и закрывает процесс агента.

- `components/workspace-shell.tsx` — оболочка, навигация, поиск, проекты и настройки.
- `components/agent-chat.tsx` — сообщения, действия, разрешения, ответы на вопросы, остановка.
- `components/machines-panel.tsx` — SSH, графики, доступы и управление установкой/входом.
- `runner/hub.mjs` — проекты, жизненный цикл диалогов, нативные адаптеры, мониторинг.
- `runner/agent-rpc.mjs` — ограниченный по размеру JSON-RPC-транспорт, таймауты и разрыв соединения.
- `runner/machine-process.mjs` — запуск фиксированных операций локально / через проверенный SSH.
- `runner/accounts.mjs` — зашифрованные аккаунты, выбор для машин/чатов, перенос и отзыв доступа, сериализация refresh.
- `runner/account-brokers.mjs`, `runner/agent-profile.mjs` — изолированная авторизация штатными CLI и профили чатов.
- `runner/connectors.mjs`, `runner/connector.mjs` — исходящий WSS-коннектор для Windows/macOS/Linux.

Панель использует тот же защищённый API runner, что и прежний проект. Для диалогов добавлен `/api/hub`; старые данные находятся в прежней SQLite. Метаданные новых проектов и диалогов хранятся в `settings` с явным `recordType`, а заголовки, сообщения и ожидающие разрешения — в зашифрованном `secret`. Это позволяет обновиться без разрушительной миграции старых таблиц. Прежние развёртывания выдаются отдельно как `services`. Ранее автоматически импортированные записи папок транзакционно превращаются в `service_context`; их диалоги получают `projectId: null`, сохраняя `cwd`, нативный ID и зашифрованную историю. Новые проекты создаются явно.

Для чата без проекта сервер определяет домашний каталог: локально через ОС, по SSH через проверенное соединение, у коннектора — из валидированной метрики `homePath`. Рабочий каталог фиксируется в `session.cwd`. Для Codex без проекта по умолчанию выбран `read-only`. Перенос разрешён только между папками одной машины, требует остановки активного хода и закрывает процесс протокола перед возобновлением с прежним нативным ID. Удаление проекта из списка отсоединяет чаты, сохраняя их каталог; файловые операции при этом не выполняются.

## Три транспорта машин

1. **SSH:** Linux-сервер любого провайдера, проверка SHA-256 host key при каждом соединении. Можно использовать отдельного пользователя. Терминал — PTY поверх WebSocket с одноразовым билетом, привязанным к Origin и машине.
2. **Локально:** машина runner. Поддерживаются Windows, macOS, Linux, запуск без shell-интерполяции. Секреты инфраструктуры `EZDEPLOY_*` исключаются из окружения дочернего агента.
3. **Коннектор:** машина сама открывает WSS к `/api/connector`. Начальное сопряжение одноразовым кодом (5 минут), затем отдельный постоянный ключ машины. Ключ на панели зашифрован, на компьютере находится в профиле владельца. Повторное сопряжение — `--pair`. Ключ нельзя использовать для доступа к административному HTTP API. Браузерные подключения с Origin к сокету коннектора отклоняются. Отзыв разрывает соединение и инвалидирует ключ.

У коннектора есть только операции из фиксированного списка: агент, версия, установка фиксированного агента (native OpenCode на POSIX, известный npm-пакет для остальных вариантов), штатный вход. Нет универсального RPC «выполни произвольную shell-команду». При потере связи коннектор завершает запущенные им процессы, затем пытается восстановить соединение. Это не откатывает уже записанные файлы и фоновые службы, созданные агентом.

## Агентские протоколы

**Codex:** app-server по stdio, `initialize`, `thread/start`/`thread/resume`, `turn/start`, события сообщений/команд/файлов и `turn/interrupt`. Режимы: `read-only` или `workspace-write`, `approvalPolicy: on-request`. Дополнительный доступ выдаётся на одно действие. Device-code login работает в отдельном временном профиле машины панели; результат зашифрован в vault. Целевой процесс получает внешний `chatgptAuthTokens` с `experimentalApi`, без refresh token. Запросы `account/chatgptAuthTokens/refresh` обрабатывает панель, объединяя одновременные обновления. API-ключ использует штатный login. До сохранения сообщения проверяется готовность аккаунта.

**OpenCode:** ACP по stdio, `initialize`, `session/new`/`session/load`, `session/prompt`, `session/update`, `session/request_permission`, `session/cancel`. Загрузка проверяет объявленную поддержку `loadSession`; реплей не дублирует сохранённые сообщения. `OPENCODE_PERMISSION={"*":"ask"}` задаётся для процесса. Интерфейс принимает только `allow_once`/`reject_once`. ACP не является OS-песочницей: после разрешения действие выполняется с правами пользователя машины. Клиент не объявляет файловые или терминальные capabilities от своего имени.

Неизвестные запросы агента получают отказ JSON-RPC, а не автоматическое разрешение. Лимит — 16 одновременно открытых процессов протокола, 12 на коннекторе, один ход — 30 минут. После рестарта ход помечается прерванным; автоматического повтора нет. Отправка в уже активный диалог отклоняется. В одной папке проекта одновременно работает только один диалог с правом записи; read-only диалоги могут работать рядом. История возобновляется по нативному ID при следующем сообщении.

Claude Code — необязательное дальнейшее расширение, сейчас адаптер не добавлен.

## Аккаунты и профили

Записи `agent_account` содержат публичное имя, провайдера, состояние и зашифрованные credentials. Авторизация не затрагивает обычные профили CLI владельца. Codex использует app-server, OpenCode — временный loopback-сервер со случайным Basic-паролем и проверкой, что анонимный доступ возвращает 401. OAuth-ссылки допускают только HTTPS. Браузеру возвращаются метаданные, URL и код входа, без API-ключей и access/refresh tokens. Временные профили авторизации удаляются после завершения или отмены; незавершённый вход сбрасывается при рестарте.

У машины есть независимые настройки по умолчанию `agentAccounts`; чат фиксирует `accountId` и собственный `profileId`, поэтому изменение сервера не переключает существующие чаты. Каталог моделей кэшируется по машине, папке и аккаунту. Профили находятся только в фиксированном UUID-пространстве `~/.ezdeploy/agent-profiles/{provider}/{uuid}`; окружение не наследует ключи другого аккаунта. Передача идёт через stdin SSH/WSS, без секретов в argv. OpenCode 1 использует закрытый `auth.json`, OpenCode 2 — штатный export/import credentials и logout с конкретным ID. На POSIX каталоги имеют права 0700, файлы credentials — 0600. На Windows действуют права профиля пользователя ОС.

Для OpenCode OAuth один аккаунт получает одну активную аренду: после завершения процесса панель читает обновлённые credentials, шифрует их и удаляет копию с машины. Незавершённое сохранение фиксируется в `account_target` и восстанавливается перед следующим использованием; после повторного входа старое поколение токенов не перезаписывает новое. API-ключи допускают параллельные чаты. Отключение аккаунта запрещено во время активного хода, закрывает оставшиеся процессы, очищает vault и credentials известных профилей. У недоступных машин очистка повторяется после подключения; история профиля не удаляется. Коннектор для этих операций необходимо обновить.

## Мониторинг

SSH-машины проверяются в фоне раз в 30 секунд, открытая карточка — раз в 10 секунд. Локальная машина и коннектор — раз в 10 секунд. На машину сохраняются последние 120 измерений. CPU — разность реальных счётчиков, память и диск — показатели ОС. Входящий/исходящий трафик Linux читается из `/proc/net/dev`; скорость вычисляется только между корректными последовательными счётчиками, сброс после перезагрузки не превращается в отрицательную скорость. На платформах без доступного сетевого счётчика показывается отсутствие данных. IPv6 показывается только при его наличии.

## Граница безопасности

Версия для **одного владельца**. Административный bearer token даёт доступ ко всем добавленным машинам. Вкладка держит вручную введённый токен только в памяти. Для удалённого подключения допускается HTTPS; runner по умолчанию слушает 127.0.0.1. CORS ограничен списком Origin, ответы API используют `no-store`. Локальный dev-прокси добавляет токен только на серверной стороне.

Для размещения в интернете обязательны TLS и отдельная аутентификация владельца на reverse proxy либо доступ через VPN. Нельзя публиковать dev-сервер с автоматической подстановкой административного токена без такого контроля. Уровни доступа, пользователи/организации, E2E-шифрование между браузером и машинами и неизменяемый журнал аудита ещё не реализованы. Панель расшифровывает историю для владельца; шифрование на диске не является E2E.

Не запускайте агента под root без необходимости. Папка проекта задаёт контекст; ограничения Codex обеспечивает его собственная песочница. Штатные настройки MCP/skills на машине также являются доверенным кодом. Данные проектов и сообщения отправляются выбранному агентом провайдеру в соответствии с его настройками.

## Совместимость

Старые модули деплоя сохранены для обратимости и существующих данных. В обычном запуске runner их API, webhooks и root-LLM-оператор отключены. Включение возможно только явно: `EZDEPLOY_LEGACY_API=true`. Старый интерфейс не входит в новую страницу. Справочник прежнего режима — `docs/legacy-deployment.md`; это архив, а не описание нового основного интерфейса.

## Проверки и источники протоколов

Тесты проверяют API-аутентификацию, шифрование сообщений/заголовков, фиксацию машины/папки, запрет параллельного хода, одноразовые разрешения, остановку, ACP-ответ, ограничение команд коннектора, повторное подключение и отзыв. Сетевые тесты используют loopback и имитируют нативный процесс без платных запросов к моделям. Отдельно проверен handshake установленного Codex без inference.
