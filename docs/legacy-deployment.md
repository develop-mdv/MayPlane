# MayPlane

Русскоязычная веб-панель для управления проектами на нескольких Linux-серверах. Первая версия для одного владельца: Docker Compose и сохраняемые Bash-сценарии, публичные и приватные GitHub-репозитории по HTTPS и SSH под root. Панель и исполнитель запускаются отдельно.

## Что работает

- Проекты, серверы, поиск и фильтрация, история операций и логи.
- Добавление SSH-сервера с проверкой SHA-256 ключа и входом по паролю или ключу без passphrase.
- Установка Docker, Compose v2 и Git на Ubuntu 24.04 и 26.04 по кнопке.
- Ввод и редактирование `.env` в карточке, необязательная загрузка файла, шифрование секретов AES-256-GCM, SQLite для постоянных данных.
- Проверка сборки без запуска, деплой, перезапуск и остановка Docker Compose. Несколько проектов на сервере имеют отдельные Compose project names.
- GitHub push webhook с HMAC-SHA256, проверкой репозитория/ветки и защитой от повторной доставки.
- Снимок CPU/RAM/диска при подключении или нажатии «Проверить», последние 200 строк контейнерных логов.
- Перенос образов, каталога проекта и управляемых Docker volumes с остановкой контейнеров, проверкой SHA-256 и возвратом к источнику при ошибке, когда это можно подтвердить безопасно.
- Интерактивная SSH-консоль в разделе «Серверы»: PTY, Ctrl+C, resize, сохранение текущего каталога внутри сеанса.
- GitHub Personal Access Token, список репозиториев аккаунта и доступ к приватным репозиториям.
- Только реальные данные исполнителя. При недоступном API показывается ошибка подключения, примеров и имитации действий нет.

## Помощник деплоя и LLM

В «Настройки → Помощник деплоя» укажите Base URL, Model ID и API-ключ. По умолчанию выбраны AllTokens:

- Base URL: `https://api.alltokens.ru/api/v1`
- Model ID: `google/gemini-3.8-flash`
- Протокол: OpenAI-compatible `POST /chat/completions`.

Настройки подходят также для OpenRouter и других совместимых сервисов. Для локальных моделей разрешён HTTP на localhost/127.0.0.1. Нативные протоколы Anthropic/Gemini отдельно не реализованы — используйте их через совместимый шлюз. [Документация API AllTokens](https://docs.alltokens.ru/api/chat-completions/).

Ключ хранится зашифрованным в SQLite и не возвращается в API состояния. Сохранение ключа не вызывает модель; «Проверить сохранённое подключение» выполняет короткий платный запрос. При изменении Base URL требуется заново ввести ключ, чтобы прежний ключ не ушёл другому провайдеру. Один запрос к модели ограничен 90 секундами; план — 10 000 выходных токенов, шаг чата — 9000. Один ход чата ограничен 14 шагами, после трёх подряд ошибок выполнение останавливается. Расход токенов виден в карточке и чате.

**Создание проекта:** введите GitHub-репозиторий, выберите тип, сервер и при необходимости домен. Имя предлагается из URL, пустая ветка определяется через GitHub. «Создать проект» сохраняет карточку и окружение без деплоя. Затем проверьте настройки в карточке и отдельно запустите «Развернуть» или подготовьте план во вкладке «План». Для приватного репозитория сначала выберите GitHub-подключение.

**Существующий проект:** откройте вкладку «План». «Подготовить план» только анализирует; «Подготовить и развернуть» продолжает до запуска, если достаточно данных. План содержит объяснение, рабочую папку, переменные, прочитанные файлы и созданные конфигурации. Если не хватает ключей, внесите их во вкладке «Переменные», затем нажмите «Развернуть по этому плану». Если изменилась ветка или параметры проекта, повторите анализ. «Объяснить последнюю ошибку» обращается к LLM и сохраняет рекомендации без выполнения команд.

Исполнитель читает дерево GitHub и до 24 небольших манифестов/инструкций, суммарно до 160 КБ. Значения .env, SSH-, GitHub- и LLM-ключи не включаются в запрос. Из .env.example используются только имена переменных. Известные секреты и распространённые форматы ключей маскируются; хранить неизвестные секреты в README/манифестах всё равно не следует. Приватный код из выбранных файлов отправляется вашему LLM-провайдеру при включённом анализе.

**Чат проекта и сервера:** вкладка «Чат» в проекте и кнопка «Чат» в разделе серверов принимают задачи обычным текстом. Модель получает контекст репозитория/сервера, выполняет команды по SSH, видит их вывод и может исправить ошибку следующим шагом. Стек и способ запуска не ограничены шаблонами: можно подготовить сборку, файлы, зависимости, systemd или контейнеры по требованиям проекта. Команды выполняются от root сразу; история сообщений, команд и результатов хранится зашифрованной. «Прервать выполнение» в чате или в логах отменяет ожидание модели, прерывает текущую SSH-команду и отменяет следующие шаги. Команда ограничена 10 минутами; после перезапуска исполнителя задания автоматически не повторяются.

Во вкладке «Логи» выберите выполняемую операцию и нажмите «Прервать выполнение». Доступно для деплоя (включая автонастройку и применение плана), сборки, перезапуска, анализа и чата. Задание в очереди отменяется без подключения к серверу. Выполняемое задание удерживает блокировку сервера до завершения команды; если SSH не подтвердил остановку, журнал сообщает об этом. Уже внесённые изменения и запущенные фоновые службы не откатываются: проверьте состояние приложения перед повтором. Перенос, удаление и подготовка сервера этим способом не прерываются.

**Сценарий управления:** помощник сохраняет команды deploy, stop, remove, check, logs и дополнительные файлы. Кнопки «Развернуть», «Остановить», «Удалить», получение логов и GitHub webhook воспроизводят их без LLM. Перед деплоем исполнитель обновляет Git, загружает окружение и восстанавливает файлы; после запуска выполняется check. Команды можно просмотреть и изменить вручную в «Обзоре». Данные следует хранить в MAYPLANE_DATA_DIR отдельно от каталога Git. Удаление требует подтверждения; карточка удаляется только при выбранном флажке и успешном выполнении команды. Сценарии stop/remove должны сохранять данные; произвольный Bash работает с полномочиями root, поэтому это требование к сценарию, а не файловая песочница.

План сохраняется отдельно от действующего сценария. «Развернуть по этому плану» применяет сохранённые команды без повторного вызова модели. Если ключей или сведений недостаточно, помощник задаёт вопрос; заполните поля переменных и продолжите в чате. Отсутствие готового Dockerfile или нестандартный язык само по себе не блокирует настройку. Доступы к внешним сервисам и решения владельца модель не может получить самостоятельно.

Без LLM остаётся встроенное автоопределение типовых Docker Compose/Dockerfile, Node.js, Python, Go и статических сайтов. Ограничения этого встроенного режима не распространяются на сценарии, подготовленные в чате.

Созданные `mayplane.compose.yaml`, `mayplane.Dockerfile` и конфигурация Nginx хранятся отдельно от отслеживаемых файлов. Изменения не коммитятся и не отправляются в Git. .env исключается из build context; публичные VITE_/NEXT_PUBLIC_/REACT_APP_ переменные передаются в сборку. Постоянные данные по умолчанию сохраняются в /app/data; другие каталоги требуют настройки томов. Автоматический режим отклоняет привилегированные контейнеры, host namespaces, Docker socket и пути вне проекта. Dockerfile и package scripts из репозитория должны быть доверенными.

### Домен и HTTPS

Для сгенерированного сайта выбирается свободный порт 18080–18179. После запуска проверяется HTTP-ответ; статус и дальнейшие действия показаны в карточке. HTTP 4xx подтверждает ответ сервера, но не корректность всех функций приложения. Порт может потребовать открытия в firewall провайдера.

Если DNS домена указывает непосредственно на выбранный VPS, а 80/443 свободны, исполнитель создаёт общий Caddy-прокси в `/opt/mayplane-proxy` с отдельными томами сертификатов. Новые проекты добавляются к существующим маршрутам mayplane. Конфигурация проверяется перед применением; при ошибке reload восстанавливается предыдущий файл. [Команды Caddy](https://caddyserver.com/docs/command-line#caddy-validate).

Встроенная кнопка настройки домена не перенастраивает занятые порты, чужой proxy или DNS/CDN на другом адресе: в карточке будет инструкция с точным upstream. DNS у регистратора и firewall остаются действиями пользователя. После изменений нажмите «Настроить домен». TLS может выдаваться несколько секунд или дольше; панель не утверждает, что сертификат уже выпущен, пока он не проверен отдельно. Внешние БД, секреты провайдеров, OAuth и исправления приложения требуют соответствующих доступов или действий.

Переменные в карточке помечаются как обязательные, необязательные или ещё не определённые. Помощник указывает назначение и известный несекретный дефолт. Пустые обязательные поля блокируют деплой; пустые необязательные остаются в редакторе, но не передаются при запуске, чтобы приложение применило свои настройки. Заданные значения сохраняются. Для Compose учитываются операторы обязательности и значений по умолчанию ([документация Docker](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)). Само наличие имени в .env.example не означает обязательность. У старых планов новая классификация уточняется при повторном анализе.

## Локальный запуск

Требуется Node.js 24 и npm. Выполняйте команды в папке проекта:

```sh
npm ci
npm run runner:setup
npm run runner
```

В другом терминале:

```sh
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000). Локальная панель автоматически подключается к исполнителю через Vite proxy `/api`, включая WebSocket. Dev-сервер привязан к `127.0.0.1`; ключ из `.env.runner` добавляется прокси и не попадает в клиентский JavaScript. После создания `.env.runner` перезапустите dev-сервер.

«Исполнитель» — серверная часть MayPlane: она хранит данные, подключается по SSH ко всем вашим VPS и выполняет операции. Один исполнитель управляет несколькими серверами. В настройках можно указать адрес другого исполнителя и `MAYPLANE_TOKEN`; при ручном подключении ключ хранится в памяти вкладки.

Файл `.env.runner` создаётся один раз и не перезаписывается. `MAYPLANE_ENCRYPTION_KEY` расшифровывает секреты в `.runner-data/mayplane.sqlite`. Резервируйте **базу вместе с ключом**, храните их вне Git. Резервную копию SQLite делайте после остановки исполнителя либо штатным SQLite backup API; не копируйте только основной файл во время записи WAL.

## Доступ к исполнителю с опубликованной панели

Панель в Sites сама не устанавливает SSH-соединения. Разместите `runner` на своём сервере и выдайте ему HTTPS-адрес через обратный прокси. HTTP допустим только для локального запуска; HTTPS-панель и браузер могут запрещать подключение к локальной сети.

В `.env.runner`:

```dotenv
HOST=127.0.0.1
PORT=8788
ALLOWED_ORIGINS=https://your-panel.example.com,http://localhost:3000
MAYPLANE_PUBLIC_URL=https://runner.example.com
```

Пример Caddy:

```caddyfile
runner.example.com {
    reverse_proxy 127.0.0.1:8788
}
```

Не открывайте незашифрованный порт исполнителя в интернет. Авторизация — один длинный ключ владельца, без регистрации/ролей/команд. CORS разрешает только перечисленные origins; вызовы без Origin (GitHub, CLI) всё равно проверяют ключ или подпись webhook.

Исполнитель можно запустить контейнером:

```sh
npm run runner:setup
docker compose -f compose.runner.yaml up -d --build
```

Порт контейнера привязан к loopback хоста. Данные сохраняются в отдельном named volume. Docker socket хоста исполнителю не нужен: он управляет целевыми серверами через SSH.

## Первый проект

1. «Серверы → Добавить сервер»: IP, порт, root-доступ. Сравните отпечаток с консолью своего VPS. Например, на сервере: `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256`. Тип ключа должен совпадать с согласованным SSH-ключом; fingerprint API показывает выбранный ключ сервера.
2. Если Docker отсутствует, нажмите «Настроить сервер». Установка рассчитана на Ubuntu 24.04 и 26.04. Уже подготовленные Linux-серверы с Bash, Git, Docker и Compose v2 тоже можно подключать.
3. «Новый проект»: HTTPS URL, ветка, тип, сервер, Compose-файл и `.env` до 64 КБ. Для приватного репозитория выберите подключённый GitHub-аккаунт. `.env` можно вводить текстом, а затем менять через проект → «Переменные» → «Редактировать сохранённые значения». Поддерживаются однострочные `KEY=value`, комментарии и кавычки; многострочные значения отклоняются.
4. Откройте проект и нажмите «Развернуть». Рабочие каталоги: `/opt/mayplane/<uuid>/repo`. Не вносите туда ручные изменения: Git обновляется через `reset --hard`. Данные приложения храните в named volumes или bind mounts, которые не отслеживаются Git.
5. Compose использует имя `mayplane_<uuid>`. Не задавайте общие `container_name`, имена сетей и порты для разных проектов. Панель не выбирает свободные порты автоматически.

Для вложенного Compose-файла, например `tg-wife-ai/docker-compose.yml`, рабочим каталогом будет `repo/tg-wife-ai`, `.env` записывается рядом с Compose. «Проверить сборку» клонирует Git и собирает Docker-образы, не запуская контейнеры. Обязательные переменные проекта (`requiredEnvKeys` в API) проверяются перед запуском.

Пример приложения с проверкой состояния и сохраняемыми данными находится в `examples/node-app/`. Поместите его содержимое в свой репозиторий. Переменные для приложения задавайте в Compose через `environment` или `env_file: .env`; автоматическая подстановка Compose сама по себе не передаёт все переменные в контейнер.

`up --wait` проверяет Compose healthcheck, если он объявлен; без healthcheck проверяется только запуск контейнера. Добавляйте проверку готовности приложения и базы данных. В ручном режиме домен — метка. В режиме помощника доступны проверка DNS и управляемый HTTPS-прокси при свободных портах.

## Приватные GitHub-репозитории

В «Настройки → GitHub» введите Personal Access Token. Для fine-grained token выберите владельца и нужные репозитории, разрешение **Contents: Read-only**; Metadata добавляется GitHub автоматически. [Инструкция GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). У организации может потребоваться одобрение токена. После подключения выберите аккаунт и репозиторий при создании проекта. Список загружается страницами по 100 записей. Повторное подключение того же аккаунта обновляет его токен для всех связанных проектов.

Токен шифруется в SQLite. На целевой сервер перед Git-операцией передаётся временный файл с правами 0600 в защищённом каталоге вне проекта. Git получает заголовок авторизации только для HTTPS URL выбранного репозитория GitHub; редиректы отключены. Файл удаляется перед сборкой и при ошибке. Токен не записывается в URL origin, .gitconfig, очередь или логи. Деплой публичного репозитория не требует токена.

## Консоль сервера

«Серверы → Консоль» открывает настоящую оболочку по SSH с проверкой сохранённого ключа хоста. Команды идут с правами root. Можно менять каталог, запускать интерактивные команды и прерывать их Ctrl+C. Закрытие окна или «Отключить» завершает SSH-сеанс; повторное подключение создаёт новый сеанс.

WebSocket использует одноразовый билет на 30 секунд, привязанный к серверу и Origin панели. Основной API-ключ не передаётся в URL. До 8 одновременных сеансов, отключение после 30 минут без ввода и предельная длительность 6 часов. Обратный прокси должен поддерживать WebSocket upgrade (Caddy reverse_proxy поддерживает его).

Панель не записывает терминальную сессию и не маскирует её вывод. История команд может сохраняться оболочкой самого сервера. Маскирование секретов действует в логах операций и контейнеров.

## CI/CD

Укажите `MAYPLANE_PUBLIC_URL`, откройте проект → CI/CD, включите автодеплой и создайте секрет. Добавьте URL и секрет в GitHub → Settings → Webhooks: `application/json`, `Push events`. Секрет показывается только при выпуске; перевыпуск требует обновления GitHub.

Исполнитель принимает только подписанный push в сохранённую ветку указанного репозитория. При занятом сервере webhook возвращает 409: используйте Redeliver в GitHub после завершения операции. Это простая очередь одного исполнителя; автоматические повторы и планировщик пока отсутствуют. Деплой забирает актуальный HEAD ветки, а не обязательно SHA конкретного события.

Workflow `.github/workflows/ci.yml` проверяет сам MayPlane: тесты, типы и сборку. Автодеплой управляемых проектов выполняет webhook-исполнитель.

## Перенос и ограничения

В карточке работающего проекта нажмите «Перенести», выберите сервер и выполните «Проверить перенос». Проверка не останавливает приложение: показывает контейнеры/службы, каталоги, тома, объём данных, зависимости и препятствия. В дополнительных настройках можно указать другие каталоги, службы systemd и команду проверки приложения. После проверки подтвердите состав данных и допустимость простоя. План действует 30 минут; перед остановкой состав проверяется ещё раз.

В форме можно выбрать **обычный перенос** или **перенос с LLM**. В режиме LLM используется провайдер из настроек: помощник читает сведения о запуске, список файлов и описание репозитория, учитывает предыдущую ошибку, предлагает дополнительные пути/службы и команды для целевого сервера. Значения окружения, SSH-ключи и пароли в контекст модели не включаются. План показывает команды подготовки, настройки после копирования и проверки; выполнение требует подтверждения показанного плана. Подготовка выполняется до простоя, затем все проверки повторяются. Устранимые зависимости показаны отдельно, а конфликты данных, портов и ресурсов остаются блокирующими. Команды сохраняются и выполняются без повторного обращения к модели. Произвольный способ запуска сначала нужно оформить как Docker или systemd; LLM не отключает проверки копирования.

Если обычный перенос завершился ошибкой после возможного запуска новой копии, в форме восстановления также доступен режим LLM. Помощник составляет отдельный план исправления текущего приложения на цели. После подтверждения выполняются его команды и проверки; старые архивы не копируются поверх новых записей. План восстановления действует 30 минут и привязан к конкретному переносу и SSH-идентичности обоих серверов.

Поддерживаются Docker/Compose, в том числе уже привязанные приложения, и пользовательские службы systemd. Docker переносится без пересборки: сохраняются изменения внутри контейнеров, именованные и анонимные локальные тома, bind mounts, окружение, настройки запуска, сети и опубликованные порты. Для systemd копируются unit-файлы, drop-in, рабочие каталоги, EnvironmentFile и каталоги данных, указанные в службе. Другие пути добавляются вручную. После переноса стандартные кнопки управления работают с новой привязкой; прежний сценарий сохраняется в зашифрованной записи, автодеплой отключается до настройки обновлений.

Порядок: проверка → отключение автозапуска источника → корректная остановка записи → архивирование → SFTP с SHA-256 → распаковка → сравнение содержимого, UID/GID, прав, ACL/xattrs и ссылок → запуск → Docker healthcheck/проверка служб и дополнительная команда. Для веб-проекта с известным HTTP-портом проверяется ответ HTTP. Смена сервера в карточке происходит после проверок. Исходные файлы и архивы в `/opt/mayplane-migrations/<job-id>` остаются на месте; очистка не выполняется автоматически.

На обоих серверах нужны root, Python 3, GNU tar, coreutils и свободное место. Для Docker нужны локальный Docker Engine, curl и ss (iproute2). Архитектуры CPU должны совпадать; для native-служб также нужны одинаковая ОС/версия, необходимые библиотеки и пользователи с теми же UID/GID. Проверка отклоняет конфликты путей, имён, портов, недостаток места, общие тома/сети, внешние драйверы, неподдерживаемые namespaces и системные каталоги. Ссылки на невыбранные данные и жёсткие ссылки за границы архива блокируют перенос.

Если ошибка возникла **до попытки запуска цели**, исполнитель восстанавливает исходное приложение. Если новая копия уже могла записать данные, старый снимок не возвращается автоматически: обе копии сохраняются, дальнейшие операции блокируются, в форме появляется «Восстановить запуск на новом сервере». Восстановление не копирует старые данные поверх новых. Блокировка и этап переноса сохраняются при перезапуске исполнителя, независимо от размера истории логов. Частично восстановленные ресурсы на цели сохраняются для проверки; повторный перенос блокируется до освобождения конфликтующих ресурсов.

Перенос выполняется с простоем. Внешние БД/S3, DNS, сертификаты общих reverse proxy, правила firewall/NAT и зависимости вне перечисленных файлов автоматически не переносятся. Для домена панель показывает необходимость переключить DNS/proxy и проверить HTTPS. Для VPN, внешних хранилищ и необычных способов запуска нужно дополнить план и проверку приложения; целостность файлов сама по себе не подтверждает работу внешних сервисов.

Статус проекта — результат последней операции, а не непрерывный мониторинг. Метрики серверов и логи приложения запрашиваются вручную. API возвращает последние 100 операций (полная история остаётся в SQLite), до 2000 строк на операцию; нужен собственный долгосрочный сбор логов. Просмотрщик логов маскирует точные значения `.env`; приложения не должны печатать секреты в другом кодировании.

Это MVP для доверенных репозиториев и одного владельца. Dockerfile/Compose выполняют код с широким доступом к целевому серверу. Приватные репозитории других Git-провайдеров, интеграции DNS-регистраторов, роли, расписания бэкапов, непрерывный мониторинг, беспростойный деплой и перенос внешних БД ещё не реализованы.

## Kubernetes

Встроенный исполнитель использует Docker Compose; сохранённые команды могут вызывать другие установленные инструменты. Отдельной интеграции управления кластерами пока нет. Kubernetes разумно добавить отдельным способом развёртывания, когда нужны реплики приложения, несколько узлов, распределение нагрузки и обновления кластера. Сам переезд панели с локального компьютера на VPS не требует Kubernetes. Прототип можно сделать локально через [kind или minikube](https://kubernetes.io/docs/tasks/tools/). Для данных нужен отдельный план хранения и миграции: [локальный PersistentVolume привязан к узлу](https://kubernetes.io/docs/concepts/storage/volumes/#local).

## Привязка уже работающего приложения

Создайте карточку проекта, затем откройте «Обзор» → «Проверить на сервере и привязать». При необходимости укажите абсолютный каталог приложения. После поиска выберите найденный вариант и нажмите «Привязать это приложение».

Поиск и привязка выполняют только чтение по SSH, без LLM, установки пакетов и перезапуска процессов. Поддерживаются группы Docker Compose, отдельные Docker-контейнеры и пользовательские службы systemd. Для другого менеджера можно привязать каталог и через чат сохранить команды управления. Поиск ограничен 150 контейнерами и 150 загруженными службами; Git проверяется для первых 30 вариантов. Перед привязкой повторно проверяются ресурсы, каталог, актуальность поиска (30 минут) и отсутствие другой привязки.

В панели сохраняются исходные имена/ID ресурсов, статус процессов, порты и точки монтирования, сведения Git, доступные файлы конфигурации и окружение. Полный `docker inspect`, unit systemd, файлы конфигурации и переменные шифруются в SQLite. Окружения нескольких контейнеров сохраняются раздельно: различающиеся значения не смешиваются в один `.env`. Снимок можно скачать из карточки; он содержит секреты и **не является резервной копией данных приложения**. Привязка заменяет прежний сценарий и окружение карточки, отключает автодеплой; исходные файлы и данные сервера не изменяются.

После привязки:

- «Запустить», перезапуск, остановка, проверка состояния и логи используют исходные ID контейнеров или имя службы без LLM. Статус описывает процесс/контейнер и его Docker healthcheck, а не обязательную проверку доступности сайта извне.
- «Запустить» запускает существующие ресурсы; Git автоматически не обновляется. Для обновлений и CI/CD сохраните через чат свой сценарий в исходном каталоге. Автоматический checkout и перезапись `.env` для привязок отключены.
- Во вкладке «Переменные» доступен снимок только для просмотра. Изменяйте текущую конфигурацию через чат или SSH; снимок отражает момент привязки.
- Удаление Docker-развёртывания удаляет только привязанные контейнеры, сохраняя сети, volumes и файлы. Для systemd останавливает службу и отключает её автозапуск, оставляя unit и данные. Восстановление удалённых контейнеров требует сценария развёртывания.
- «Отвязать» удаляет связь в панели и сценарий; приложение на сервере продолжает работать. При необходимости его можно найти и привязать заново.
- Перенос доступен для Docker/Compose и systemd через предварительную проверку состава данных. Дополнительные каталоги и зависимости указываются в форме переноса.

### Удаление карточки из панели

В обзоре проекта есть отдельная кнопка «Удалить из панели». После подтверждения удаляются карточка, её сохранённые переменные, чат и сценарии. SSH-команды не выполняются: приложение и все данные на сервере остаются. Автодеплой через удалённую карточку прекращается. История операций сохраняется, в неё добавляется запись об удалении. Удаление блокируется во время операций и незавершённого переноса. «Удалить развёртывание» остаётся отдельным действием для удаления ресурсов на сервере.

### Несколько экземпляров одного проекта

Один репозиторий и одинаковое название можно использовать в нескольких карточках — на разных серверах или на одном. У каждой карточки собственный ID, окружение, сценарий, webhook и история операций. Имя служит подписью: поддерживаются буквы, цифры, пробелы, точки, дефисы и подчёркивания (1–80 символов). Сервер и короткий ID помогают различать экземпляры в карточках и списках выбора. На одном сервере конфигурация приложений должна использовать свободные порты и отдельные имена явно заданных ресурсов.

При первом запуске новой версии исполнитель автоматически снимает старое ограничение уникальности имени в одной транзакции SQLite, сохраняя ID, конфигурацию и зашифрованные значения существующих проектов.

### Ожидание LLM и завершение операций

Запросы к провайдеру используют потоковый ответ (SSE). Получение данных продлевает ожидание: отсутствие данных ограничено 90 секундами, весь запрос — 10 минутами. Короткая проверка провайдера ограничена 20 секундами. Сетевые ошибки, отсутствие средств, обрыв потока и таймауты различаются; частичный JSON не выполняется. Для планирования переноса прогресс ожидания отображается в журнале. Провайдеры, которые возвращают обычный JSON вместо SSE, тоже поддерживаются.

В списке логов и выбранной операции виден статус завершения, а также время начала и окончания. «Нужно продолжение» означает, что выполнение остановлено и требуется следующий шаг в чате.

Для Docker в дополнительных параметрах переноса можно выбрать SIGTERM, SIGINT или SIGQUIT, если приложение обрабатывает этот сигнал корректно. LLM также может предложить сигнал в проверяемом плане. Выбор сохраняется в конфигурации целевого контейнера. Принудительное завершение с кодом 137 по-прежнему блокирует копирование; резервная исходная копия сохраняется.

При переносе между разными хранилищами Docker идентификатор образа после загрузки может измениться. Панель определяет ID на целевом сервере и сверяет конфигурацию, архитектуру и контрольные суммы слоёв с исходным снимком. Несовпадение содержимого блокирует запуск.


План LLM переноса сохраняется у проекта и доступен после закрытия панели и перезапуска исполнителя. «Проверить серверы по сохранённому плану» обновляет проверку на 30 минут без нового запроса к провайдеру; генерация и её дата сохраняются отдельно. Изменение состава приложения или SSH-подключений требует нового плана. Неудачная новая генерация не удаляет предыдущий план.

В переносе с LLM можно выбрать «Сохранить остановленную копию в архиве». Панель определяет конфликтующие контейнеры, службы, каталоги, локальные тома и сети и показывает полный состав перед подтверждением. Проверяются владельцы ресурсов, общие хранилища, открытые для записи файлы и изменения после проверки. Для работающей изолированной копии выберите «Подготовить автоматически». Общие ресурсы требуют другого сервера либо отдельного решения. Сначала создаётся архив прежней целевой копии, проверяется восстановление файлов с содержимым и метаданными; только затем освобождаются имена. Исходное приложение продолжает работать до окончания подготовки. Путь и состояние архива остаются в проекте; приватный manifest.json, SHA-256 и журнал частично выполненных действий находятся в /opt/mayplane-migrations/<id>. Исходные каталоги дополнительно сохраняются рядом с суффиксом .mayplane-archive-<id>. Сбой архивирования не запускает перенос поверх существующих данных.

Архивирование конфликтов требует подтверждения состава и confirmConflictArchive в API migrate. Вопросы и препятствия можно уточнить в форме переноса; новый ответ LLM заменяет план только после генерации. Известные опасные команды удаления/остановки в новых и старых LLM-планах отклоняются; эта проверка не является песочницей для произвольного shell-кода, поэтому команды по-прежнему показываются владельцу перед исполнением.


Во вкладке «Перенос проектов» незавершённые переносы показываются отдельными карточками, включая проверки, вопросы, готовые планы и восстановление. Кнопка «Продолжить» возвращает проект, направление, план и сохранённый выбор. Карточка хранится у проекта, поэтому не зависит от последних 100 строк истории операций. Завершённый переезд не остаётся среди незавершённых.

Конфликты выбираются в верхней части окна: сохранить остановленную копию, подготовить автоматически, выбрать другой сервер или подготовить вручную. Выбор архивирования отвечает на прежний стандартный вопрос LLM без повторного запроса к провайдеру; остальные вопросы остаются открытыми. Ручной выбор тоже сохраняется. «Подготовить автоматически» (stop-archive) сначала штатно останавливает только проверенные изолированные ресурсы цели; архив и освобождение имён происходят после проверки данных. Остановка источника начинается позже. При ошибке до освобождения ресурсов возвращается запуск только тех целевых контейнеров/служб, которые работали до подготовки. После частичного освобождения автоматический перезапуск не выполняется; stop.json содержит состояние и исходные настройки. Для остановки работающих ресурсов API migrate требует confirmConflictStop наряду с confirmConflictArchive; интерфейс включает это в существующее подтверждение состава.
